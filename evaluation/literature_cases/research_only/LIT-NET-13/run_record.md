方案 A（甲厂 1 号被覆盖、乙厂 5 号被覆盖）：

- 1 号被覆盖，+0.32；
- 2 号名次差 1，+0.026；3 号名次差 2，+0.037；4 号名次差 3，+0.060；

方案 B（甲厂 3 号被覆盖、乙厂 5 号被覆盖）：

- 1 号、2 号在生效日之前，为 0；3 号 +0.32，4 号名次差 1，+0.026；甲厂合计 0.346；

- 8 号为 0；

随机政策与目标：

- Target = 1/2×0.109125 + 1/2×0.091125 = 0.100125，即 801/8000；
- 两方案平均之差 0.018 是推迟生效的边际效果，不是目标量；
- 甲厂从 0.443 落到 0.346，差的 0.097 全部落在覆盖者之后的人身上：方案 A 有三位下游，合计 0.123；方案 B 只有一位，0.026；被覆盖者本人的 0.32 两套里都在，不构成差异；
- 目标变化版（甲厂 2、3、4 号，各 1/3）：方案 A 0.026 + 0.037 + 0.060 = 0.123，平均 0.041；方案 B 0 + 0.32 + 0.026 = 0.346，平均 173/1500；Target = 1/2×0.041 + 1/2×0.115333… = 469/6000，即 0.078166…。

这一版的目标变化版方向与全体口径相反：全体八人下方案 A 高于方案 B（0.109125 对 0.091125），只看甲厂后三位则方案 B 几乎是方案 A 的三倍（0.115333 对 0.041）。原因是 3 号在方案 B 里自己成了被覆盖者，0.32 落在评价对象内部；全体口径把这位覆盖者也计入并稀释掉，方向就被拉平。

中间值只有四位小数，没有近似替代；0.078166… 是 469/6000 的循环小数，写成 0.078167 只是展示，不参与后续计算。

## 引擎输出与手算的关系

`result.json` 的 `numeric_value` 为空，这是框架的统一行为：POINT 表示识别出可点识别的泛函，数值留给 estimation 阶段，`estimation_handoff_allowed` 为 false。上面 801/8000 与 469/6000 是对该泛函的独立手算复核，不是引擎输出。LIT-NET-09 至 12 同样如此。

引擎侧核对到的结构：原题 population 为八名父亲、权重各 1/8、两套政策分别为 `[1,0,0,0,1,0,0,0]` 与 `[0,0,1,0,1,0,0,0]`、权重各 1/2、目标类型 `FINITE_POLICY_MEAN`；目标变化版 population 为父2、父3、父4、权重各 1/3（其余位置为 0），政策不变；证书 `R1B_FINITE_SUPPORT_STOCHASTIC_POLICY_POINT_V1` 状态 VERIFIED。
